وضعیت: درخواست آمادهٔ پیاده‌سازی و تحویل پکیج به کاربر؛ این تغییر هنوز توسط چت فرانت در بک‌اند اعمال نشده است.

## کاری که از چت بک‌اند می‌خواهیم

نسخهٔ فعلی سورس بک‌اند را بررسی کن، تغییر محدود زیر را پیاده‌سازی و تست کن و یک پکیج قابل دانلود از فایل‌های تغییرکرده، همراه دستور اعمال، بررسی و Commit/Push تحویل بده. کاربر خودش فایل‌ها را در مخزن بک‌اند اعمال و Commit/Push می‌کند. در مخزن اصلی کاربر تغییر مستقیم نده؛ برای آماده‌سازی و اجرای تست‌ها از نسخهٔ کاری جدا استفاده کن. اگر سورس به‌روز در دسترس نیست، پیش از ساخت پکیج فایل‌های موردنیاز را از کاربر بخواه؛ فایل کامل قدیمی را جایگزین نسخهٔ جدید فرض نکن.

## زمینهٔ محصول

فرانت در مخزن مستقل https://github.com/hossein9473/newqc-frontend توسعه می‌یابد. نسخهٔ اتصال گزارش‌ها در Commit 56f74ef ثبت شده است. ورود ادمین و خروج با بک‌اند محلی توسط کاربر تأیید شده‌اند؛ صفحهٔ گزارش واقعی تازه متصل شده و تست زندهٔ آن هنوز انجام نشده است.

خواستهٔ قطعی کاربر این است که تمام خروجی‌های کاربردی ارزیابی جمینای، از جمله نمره، دلیل، شواهد و جزئیات ساختاری، در فرانت قابل بررسی باشند. فیلد details فعلاً از زنجیرهٔ نمایش جا افتاده است. این درخواست فقط همان فاصله را می‌بندد؛ افزودن امکانات دیگر نیاز به تصمیم جدا دارد.

## قرارداد مورد انتظار

در هر عضو answers، فیلد جدید زیر اضافه شود:

```python
details: dict[str, Any] | None = None
```

مقدار آن مستقیماً از EvaluationAnswer.details_json مربوط به همان پاسخ و همان اجرای ارزیابی بیاید.

مسیرهای مشمول:

```text
GET /api/v1/reports/calls/{call_id}
GET /api/v1/reports/calls/{call_id}/evaluation-runs/{run_id}
```

مثال ساختاری ساختگی برای قرارداد، نه تعریف کلیدهای واقعی rubric:

```json
{
  "details": {
    "sample_boolean": false,
    "sample_number": 0,
    "sample_list": [],
    "sample_nested": {"note": "نمونه", "value": null}
  }
}
```

- فیلد details همیشه در پاسخ هر AnswerDetail وجود داشته باشد؛ دادهٔ قدیمی NULL به null تبدیل شود.
- {} خالی با null یکی نشود؛ ساختارهای تو در تو، false، صفر، آرایه و رشته بدون حذف یا تبدیل به متن حفظ شوند.
- کلیدهای مثال بالا صرفاً دادهٔ تست‌اند؛ نباید به مدل کسب‌وکار یا rubric اضافه شوند.
- بقیهٔ فیلدها و معنای نمره و coverage تغییر نکنند.
- داده‌های Provider مانند کلید، header، credential و پاسخ خام نامرتبط اضافه نشوند؛ فقط details ذخیره‌شدهٔ پاسخ QC ارائه شود.

## شکل حداقلی تغییر

در backend/app/api/routes/reports.py:

```python
from typing import Annotated, Any
```

در AnswerDetail:

```python
details: dict[str, Any] | None = None
```

در ساخت AnswerDetail داخل _build_call_detail:

```python
details=answer.details_json,
```

این راهنما بر اساس نسخهٔ دیده‌شده است؛ با ساختار واقعی نسخهٔ فعلی سازگار کن. تابع مشترک باید جزئیات جدیدترین Run و Run تاریخی را مستقل و صحیح برگرداند.

## محدودیت‌های تغییر

- مجوز admin/manager/supervisor و محدودیت دپارتمان دست‌نخورده بماند؛ analyst گزارش نگیرد.
- فهرست تماس‌ها و فهرست Runها، details یا متن کامل دریافت نکنند.
- Export فعلی بدون تغییر بماند.
- انتشار مجموعه‌سؤال، مدل نمره‌دهی، Workerها، STT، prompt و داده‌های تاریخی تغییر نکنند.
- هیچ درخواست پولی AI، اجرای Worker، Migration تولیدی یا تغییر دادهٔ واقعی برای این کار انجام نشود.

## تست‌های پذیرش

تست‌های مناسب موجود، خصوصاً backend/tests/test_reports.py، را گسترش بده:

1. details تو در تو با false، صفر، آرایه و null در پاسخ آخرین اجرای مجاز دقیقاً حفظ شود.
2. details_json برابر NULL، پاسخ details: null بدهد؛ {} به {} برگردد.
3. دو Run با details متفاوت بساز؛ جزئیات تاریخی حتماً از Run انتخاب‌شده بیاید.
4. supervisor مجاز پاسخ بگیرد؛ supervisor خارج از دامنه و analyst همچنان دسترسی نداشته باشند.
5. /reports/calls و فهرست evaluation-runs جزئیات و transcript کامل را افشا نکنند.
6. مسیر اجرای ناموفق، پاسخ تکمیل‌شدهٔ قدیمی را به‌جای نتیجهٔ جاری نمایش ندهد؛ رفتار موجود حفظ شود.
7. OpenAPI فیلد nullable details را در AnswerDetail نشان دهد.

از پوشهٔ backend، دست‌کم تست‌های گزارش مرتبط اجرا شوند:

```sh
uv run pytest tests/test_reports.py
```

چک‌های لازم طبق قواعد واقعی مخزن نیز اجرا شوند. نتیجهٔ واقعی تست‌ها گزارش شود؛ بررسی انجام‌نشده با عبارت «انجام نشده» مشخص شود. تست‌ها روی دیتابیس تست جدا باشند، نه دیتابیس واقعی کاربر.

## محتوای پکیج تحویلی

- ZIP شامل فقط فایل‌های تغییرکرده با مسیر نسبی صحیح مخزن؛ فایل اصلی معمولاً backend/app/api/routes/reports.py و تست‌های مرتبط است.
- patch یا diff برای مرور تغییرات، به‌خصوص اگر فایل کامل ارائه می‌شود.
- APPLY_FA.md: نسخهٔ مبنا، فهرست فایل‌ها، نحوهٔ اعمال بدون بازنویسی تغییرات شخصی، دستور تست و روش بازگشت از همین تغییر.
- VALIDATION.md: دستورهای اجراشده، نتایج، محدودیت‌ها و موارد بررسی‌نشده.
- به‌روزرسانی مستندات قرارداد در صورت نیاز؛ از تغییر اسناد نامرتبط خودداری شود.
- دستور یا فایل OpenAPI تازه، بدون نیاز به اجرای Worker؛ اگر محیط اجازهٔ استخراج نداد، روش استخراج برای کاربر مشخص شود.
- یک پیام Commit پیشنهادی، مثلاً feat(reports): expose evaluation answer details.
- فایل‌های .env، کلیدها، دیتابیس، صوت، متن تماس واقعی، cache و محیط مجازی داخل پکیج نباشند.

## پس از اعمال توسط کاربر

کاربر تست‌ها را اجرا، فایل‌ها را مرور و سپس Commit/Push می‌کند. خروجی نهایی چت بک‌اند باید نام فیلد قطعی (details)، وضعیت null، نتیجهٔ تست‌ها و هر اختلاف با این درخواست را مشخص کند تا به چت فرانت برگردانده شود.

در فرانت فعلی، details در صورت وجود به‌شکل ساختاری نمایش داده می‌شود؛ در گام بعد با نمونهٔ پاک‌سازی‌شده از اطلاعات واقعی و rubric متناظر، نمایش خوانای تخصصی آن ساخته می‌شود. کامل‌بودن داده بر زیبایی مقدم است و کلید ناشناخته حذف نمی‌شود.
