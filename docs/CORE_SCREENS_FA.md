# مشخصات صفحات کلیدی

نسخهٔ ۰.۱ — 2026-11-09؛ طراحی رفتاری اولیه برای نمونهٔ تعاملی مرحلهٔ ۳.

## پوسته

منوی راست: نمای کلی، تماس‌ها، کارشناسان و داخلی‌ها، گزارش‌ها، آپلودها و مدیریت؛ پردازش/هزینه زیر گزارش‌های عملیاتی. نمایش مطابق نقش. بالای محتوا breadcrumb و حساب کاربر؛ تغییر رمز و خروج در منوی حساب. دامنهٔ دپارتمان در فیلتر هر گزارش مشخص باشد، نه انتخاب سراسری مبهمی که بر فرم‌ها اثر ناخواسته بگذارد.

## داشبورد

- ابتدا بازهٔ شمسی و دپارتمان مجاز؛ فیلتر منبع VoIP/Upload در صورت نیاز.
- ردیف شاخص‌ها: کیفیت، پوشش، تعداد تماس ارزیابی‌شده؛ تعریف دقیق هر شاخص مطابق پاسخ API ثبت شود.
- سپس روند و خلاصهٔ عملکرد؛ نمودار بدون داده پیام خالی دارد.
- پیوند به تماس‌های متناظر فقط با فیلتر قابل پشتیبانی؛ عنوان و بازهٔ مقصد روشن باشد.
- هیچ درصد رشد یا مقایسهٔ دورهٔ قبل بدون دادهٔ واقعی محاسبه/نمایش نشود.
- آنالیست به این صفحه هدایت نشود؛ صفحهٔ شروع او آپلودهاست.

## فهرست تماس‌ها

- فیلتر پایه: تاریخ، دپارتمان، کارشناس؛ فیلتر تکمیلی: داخلی، منبع، وضعیت پردازش، وضعیت ارزیابی، حداقل/حداکثر نمره.
- ستون‌ها: زمان تماس، کارشناس و داخلی، دپارتمان، منبع، مدت، وضعیت، کیفیت و پوشش.
- مرتب‌سازی فقط برای فیلدهای پشتیبانی‌شده در API: تاریخ، مدت، نمره.
- صفحه‌بندی سمت سرور؛ فیلترها و صفحه در URL. تغییر فیلتر صفحه را به ابتدا برگرداند.
- فیلتر داخلی صرفاً شماره است و تا افزودن API دقیق، نباید تاریخچهٔ یک انتساب خاص نامیده شود. نیاز فهرست مستقل داخلی‌ها با کاربر بررسی شود.
- در موبایل: زمان، کارشناس، وضعیت و نمره/پوشش اولویت دارند؛ باقی مشخصات با ورود به جزئیات دیده شوند.
- Export از همان فیلترهای سازگار استفاده کند؛ محدودیت خروجی پیام روشن داشته باشد.

## جزئیات تماس

- سربرگ: مشخصات تاریخی، زمان تهران، منبع، مدت و وضعیت؛ زمان فرضی Upload به‌وضوح برچسب بخورد.
- خلاصه: کیفیت و پوشش و تعداد سؤال‌های نمره‌دار؛ NULL هرگز صفر نشود.
- دسکتاپ: متن و پاسخ‌ها کنار هم؛ موبایل تب‌های متن/ارزیابی/تاریخچه، بدون از دست دادن انتخاب سؤال.
- هر سؤال: عنوان، وزن، نمره، دلیل، reason_code ترجمه‌شده، evidence، جزئیات ساختاری کامل و معیار امتیازدهی دقیق همان revision در صورت دسترسی.
- کلیک شاهد فقط با تطابق واقعی بخش متن را برجسته کند؛ در نبود تطابق، شاهد مستقل نمایش داده شود و پیوند جعلی ساخته نشود.
- نمایش دادهٔ تو در تو به‌شکل خوانا؛ مقدار false، صفر، آرایهٔ خالی و null معنای یکسان ندارند. متن یا HTML خروجی مدل هرگز به‌عنوان کد اجرا نشود.
- فیلدهای جزئیات باید از قرارداد واقعی استخراج شوند؛ برچسب‌های نمونهٔ طراحی، schema نهایی نیستند. پیش از تکمیل، ماتریس «دریافت‌شده از مدل / ذخیره‌شده / ارائه‌شده در API / نمایش در UI» تهیه شود؛ هر فاصله برای تصمیم به کاربر ارائه شود.
- خروجی مدل با دادهٔ محرمانهٔ Provider، کلید و هدر احراز هویت یکی نیست؛ این اطلاعات در صفحهٔ ارزیابی جایی ندارند.
- تاریخچه: انتخاب Run، وضعیت و نسخهٔ مربوط؛ نتیجهٔ قدیمی جای نتیجهٔ شکست‌خوردهٔ جدید نشان داده نشود.
- حالات جدا: بدون متن، متن آماده/ارزیابی در صف، شکست ارزیابی، تمام معیارها بدون نمره، موفقیت با پوشش جزئی، عدم دسترسی.

## معیار پذیرش نمونهٔ بعدی

سه صفحهٔ داشبورد، فهرست و جزئیات با دادهٔ نمایشی و ناوبری محلی؛ فیلتر نمونه و انتخاب سؤال/شاهد کار کند. حالت موبایل خوانا باشد. نمونه به API وصل نیست؛ برچسب نمایشی و همهٔ محدودیت‌ها آشکار باشند. سپس زیرساخت React و مخزن مستقل آغاز شود.
