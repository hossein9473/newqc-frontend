# تعریف محصول و نقشهٔ صفحات

وضعیت: طرح اجرایی پیشنهادی مرحلهٔ ۱، 2026-11-09.

## هدف

مدیر و سوپروایزر بتوانند کیفیت تماس را از نمای کلی تا سؤال و شاهد بررسی کنند؛ آنالیست بتواند صوت را با انتساب درست وارد و پردازش آن را پیگیری کند. تنظیمات سازمان و معیارهای ارزیابی باید با حفظ تاریخچه مدیریت شوند.

حساب ورود (User)، کارشناس مکالمه (SupportAgent) و انتساب داخلی سه موجودیت مستقل‌اند. شمارهٔ داخلی بدون مرکز تلفن هویت یکتا ندارد.

## مسیرهای اصلی

1. مدیر: ورود ← داشبورد سازمان ← دپارتمان یا کارشناس ← تماس‌های فیلترشده ← متن و پاسخ‌ها ← بررسی شواهد و نسخهٔ ارزیابی.
2. سوپروایزر: ورود ← داشبورد دامنهٔ مجاز ← تماس‌های نیازمند بررسی ← جزئیات؛ مدیریت سؤال‌ها و کارشناسان فقط در دامنهٔ مجاز.
3. آنالیست: ورود ← آپلودهای من ← ایجاد دسته با دپارتمان، انتساب داخلی و روز تماس ← ارسال فایل ← مرور و تأیید شروع ← پیگیری وضعیت.
4. مدیریت معیار: دپارتمان ← مجموعه‌سؤال‌ها ← پیش‌نویس جدید ← متن، rubric، وزن و ترتیب ← مرور ← انتشار؛ نسخهٔ منتشرشده خواندنی می‌ماند.
5. مدیریت سازمان: دپارتمان ← کارشناس ← انتساب داخلی؛ انتقال و آزادسازی به‌عنوان عملیات تاریخی نمایش داده شوند، نه بازنویسی سوابق.

## نقشهٔ مسیرهای پیشنهادی فرانت

این‌ها مسیرهای مرورگر هستند، نه endpoint بک‌اند.

| مسیر | صفحه و محتوا |
|---|---|
| /login | ورود با ایمیل و رمز |
| /dashboard | خلاصه و روند کیفیت؛ صفحهٔ نخست نقش‌های گزارش‌گیر |
| /calls | فهرست تماس، فیلتر دپارتمان/کارشناس/داخلی/روز/منبع/وضعیت/نمره، مرتب‌سازی و صفحه‌بندی |
| /calls/:id | مشخصات تاریخی، متن، نمره و پوشش، سؤال‌ها و شواهد، تاریخچهٔ ارزیابی |
| /agents | فهرست کارشناسان؛ ورودی اصلی مدیریت داخلی‌ها |
| /agents/:id | مشخصات، داخلی‌های جاری و گذشته، انتقال دپارتمان، تاریخچه و پیوند تماس‌ها |
| /reports/agents | مقایسهٔ عملکرد کارشناسان |
| /reports/departments | گزارش و روند دپارتمان‌ها |
| /reports/questions | عملکرد معیارها و پیوند تماس‌های مرتبط با revision سؤال |
| /uploads | دسته‌های قابل مشاهده؛ صفحهٔ نخست آنالیست |
| /uploads/new | انتخاب دپارتمان، انتساب داخلی، روز و ساعت اختیاری |
| /uploads/:id | ارسال فایل، مرور، شروع یا لغو پیش از شروع، وضعیت پردازش |
| /departments | فهرست دپارتمان‌ها؛ ساخت/ویرایش برای ادمین و مدیر |
| /departments/:id/question-sets | نسخه‌ها و ساخت پیش‌نویس |
| /departments/:id/question-sets/:setId | مشاهده یا ویرایش مجاز و انتشار |
| /users | کاربران قابل مشاهده، ساخت و مدیریت دسترسی مطابق نقش |
| /operations/processing | نمای پردازش، مراحل و Jobها؛ بدون کنترل Worker |
| /operations/ai-costs | هزینه، تفکیک مصرف و درخواست‌ها طبق مجوز API |
| /account | مشخصات خواندنی و تغییر رمز خود |

فرم‌های کوتاه ساخت و ویرایش داخل پنل یا دیالوگ باز می‌شوند؛ برای هر نقش کاربری صفحهٔ ساخت جدا نداریم. صفحهٔ 404، عدم دسترسی و خطای عمومی هم لازم است.

## صفحهٔ جزئیات تماس

- سربرگ: نام تاریخی کارشناس و دپارتمان، داخلی، تاریخ تهران، منبع، مدت و وضعیت.
- نمره و پوشش کنار هم؛ NULL با «قابل ارزیابی نبود» نمایش داده شود، نه صفر.
- دسکتاپ: متن مکالمه و ارزیابی سؤال‌ها کنار هم؛ موبایل: تب‌های متن، ارزیابی و تاریخچه.
- هر پاسخ: متن سؤال، وزن، امتیاز ۰/۱/۲ یا وضعیت بدون نمره، دلیل و شواهد.
- جست‌وجوی محلی متن؛ اتصال شاهد به متن تنها در صورت تطابق واقعی. API تطابق لفظی evidence را تضمین نمی‌کند.
- نسخهٔ مجموعه‌سؤال و شمارهٔ اجرای ارزیابی آشکار باشد؛ انتخاب اجرای قبلی باید نتیجه و متن همان اجرا را نشان دهد.
- نبود متن، نبود ارزیابی و شکست اجرای جدید حالت‌های جدا هستند. موفقیت قدیمی نباید شکست جدید را بپوشاند.
- تمام خروجی‌های کاربردی ارزیابی جمینای، شامل دلیل نمره، شواهد، reason_code و details ساختاری باید قابل بررسی باشند. این نیاز قطعی محصول است؛ نقص API باید پیش از تکمیل این قابلیت با مشارکت کاربر رفع شود. فیلد ناشناخته نباید بی‌صدا حذف شود؛ پس از تطبیق قرارداد، نمایش خوانا برای آن تعریف شود.
- پخش صوت نیاز جداگانه‌ای است که باید با مسیر مجاز دریافت صوت و سیاست نگهداری آن بررسی شود.

## قواعد تجربهٔ کاربری

- فارسی و RTL؛ ایمیل، شناسه، شمارهٔ داخلی و بخش‌های لاتین با جهت مناسب و بدون بهم‌ریختگی.
- تاریخ شمسی در رابط و تاریخ میلادی در API. روز تماس و روز هزینه معنای متفاوت دارند؛ برچسب فیلتر این تفاوت را روشن کند.
- فیلترهای فهرست تماس در URL حفظ شوند؛ بازگشت از جزئیات، فیلتر و صفحهٔ قبلی را نگه دارد.
- کارت‌های داشبورد فقط وقتی پیوند دارند که فیلتر مقصد واقعاً همان داده را نمایش دهد.
- حالت بارگذاری، خالی، بدون نتیجهٔ فیلتر، خطا و عدم دسترسی برای هر صفحه طراحی شود.
- رنگ تنها حامل معنا نباشد؛ متن وضعیت، کنتراست خوانا، فوکوس کیبورد و عنوان فیلدها لازم‌اند.
- جدول موبایل ستون‌های ضروری و نمایش جزئیات داشته باشد؛ صرفاً کوچک‌کردن جدول دسکتاپ کافی نیست.
- اطلاعات حساس تماس و رمزها در لاگ و دادهٔ نمونه یا مخزن ذخیره نشوند.
- خروج کاربر داده‌های حساب قبلی را از حافظهٔ رابط پاک کند؛ پنهان‌کردن منو جای مجوز بک‌اند را نمی‌گیرد.

## محدودهٔ انتشار

اولین برش قابل‌آزمایش: ورود ← فهرست تماس ← جزئیات و تاریخچه ← داشبورد پایه.

نسخهٔ اول کامل: برش بالا + مدیریت سازمان و کاربران + سؤال‌های نسخه‌دار + آپلود + گزارش‌ها و خروجی‌ها + مشاهدهٔ پردازش و هزینه + تست نقش‌ها و واکنش‌گرایی.

خارج از تعهد نسخهٔ اول بدون تصمیم جدید: ویرایش دستی نمره/متن، اعتراض و تأیید انسانی، بازیابی رمز ایمیلی، اعلان بلادرنگ، مدیریت Worker از UI، تنظیمات عمومی سامانه و صفحهٔ Audit سراسری. این قابلیت‌ها در API فعلی آماده نیستند.
